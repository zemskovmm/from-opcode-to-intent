The talk proposes a maintained intent-and-evidence workflow. It does not claim that IDD has been proven to increase productivity, that code can safely be discarded, or that the on-slide exercise is a complete Git client.

Intent-Driven Development

The practical segment draws on the distinction between durable product intent and temporary implementation work in DimonSmart / Intent-Driven Development.

  • Methodology: current intent, specifications, constraints and the distinction between intent and runtime state.
  • Specification template: observable behavior, non-goals, acceptance criteria and durable verification properties.
  • Factory benchmarking: a real runner and small fixtures, with explicit measurement limitations; not independent production-scale validation.

The comparison is about artifact lifecycles, not competing productivity promises:

  • Birgitta Böckeler: spec-first, spec-anchored and spec-as-source.
  • Spec Kit persistence models: teams choose how specifications and plans evolve.
  • Kiro specs: requirements, design and tasks.
  • OpenSpec: current specifications separated from proposed changes.

Productivity evidence is context-dependent

METR: early-2025 randomized study

16 experienced open-source maintainers working on 246 tasks in familiar repositories took 19% longer with the AI tools available during that experiment. This is a narrow causal result, not a verdict on all developers, tools or future models. Original report.

METR: February 2026 follow-up

The follow-up suggested possible improvement, but selection effects and measurement difficulties prevented a reliable estimate of the magnitude. Do not present it as a clean replacement for the earlier result. Original update.

Three field experiments

A study across 4,867 developers reported 26.08% more completed tasks with AI assistance. This is a different population and outcome metric from METR’s task-completion time; the results must not be combined into an average speedup. Microsoft Research publication.

None of these studies evaluates DimonSmart IDD itself.

Engineering observations also inform the proposed feedback loop: OpenAI on harness engineering and Anthropic on effective agents. These are not randomized tests of this methodology.

What the interactive exercise actually checks

The slide loads a recorded, synthetic Git-status fixture and classifies staged, unstaged and untracked changes. It compares the observed categories with separate, fixed expectations. A file can have both staged and unstaged changes.

The toggle deliberately omits untracked files. It is an intentionally introduced regression, not a naturally occurring AI mistake. The pass/fail result is computed by the code in your browser, rather than a prerecorded badge.

This checks categorization against one recorded fixture. It does not read your repository, invoke Git in the browser, or establish that a full Git viewer preserves files, index and refs. Application privacy and repository safety require separate evidence. A cloud coding agent used during development is a separate data boundary.

Illustrations and quotations

The storybook illustrations were generated with AI and supplied for this talk. They are visual metaphors, not historical records. Their original files and the original presentation remain unchanged.

  • The ENIAC image is an AI-assisted colorization and stylization of Reprogramming ENIAC, a 1946 U.S. Army archival photograph listed as public domain in the United States. Its colors and painted treatment are interpretive, not historically verified.
  • Frederick P. Brooks Jr., No Silver Bullet: “The hard thing about building software is deciding what one wants to say, not saying it.” The modern application to coding agents is our interpretation.
  • Lewis Carroll, Through the Looking-Glass, the Red Queen. The closing quotation is an excerpt beginning “It takes…”, with the initial letter capitalized for the slide.
